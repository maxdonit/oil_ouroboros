# Справочник параметров

По каждому параметру: что он делает, почему у него такое значение, что будет, если его увеличить или уменьшить, и
как проверить эффект. Значения — как в репозитории; итоговое значение на стенде и слой, откуда оно взялось, видны в
консоли на вкладке «Параметры».

## Где живут параметры

| Где | Что задаёт | Кто меняет | Как увидеть итог |
|---|---|---|---|
| `.env` (шаблон `.env.example`; значения по умолчанию — `src/oil_ouroboros/config.py`, `gateway/app.py`, `docker-compose.yml`) | инфраструктура: адреса, ключи, лимиты денег, модели агента, состав сервисов, сеть | администратор стенда | консоль → «Параметры» (секреты скрыты) |
| каталог `config/current/*.yaml` и промпты `config/current/prompts/` | поведение инструментов: поиск, веб, прогноз, проверка, модель субагентов | разработчик через ревью; эффект мерит eval | «Параметры», `oilo catalog show`; ссылка `слот@версия#отпечаток` — в каждом трейсе и прогоне eval |
| настройки Ouroboros (засев `ouroboros/settings.template.json`) | модели и режимы самого агента | интеграция — `.env` при каждом запуске; режимы — владелец в UI Ouroboros | «Параметры» (ключи версии агента), UI Ouroboros → Settings |
| константы в коде | время хода, окна, лимиты протокола | разработчик | раздел 4 |

## Как менять и мерить

1. **Каталог без правки файлов.** Впишите в `.env` `CATALOG_SET="retrieval.top_k=8"`, пересоздайте сервис
   инструментов (`docker compose up -d tools`) и прогоните набор:
   `docker compose exec console oilo eval --label topk8 --report var/eval_topk8.md`. Затем сравните с базовым
   прогоном: `oilo compare <id базы> <id кандидата>` (точный McNemar по кейсам). В записи прогона — каталог
   `current@версия#отпечаток`, поэтому прогоны разных вариантов не путаются. После замера уберите `CATALOG_SET`.
2. **Экспериментальный слот.** Копия `config/current/` в `config/exp-<имя>/`, правка там, `CATALOG_SLOT=exp-<имя>`.
   Каталог входит в образ (`COPY config` в `Dockerfile`): новый слот и любая правка YAML действуют после
   `docker compose up -d --build tools`. Разница с текущим — `oilo catalog diff exp-<имя>`.
3. **Живой стек.** `oilo smoke` — один ход агента (GigaChat Freemium — бесплатно, на OpenRouter около $0.01) и
   проверка того, что видела модель: инструменты, регламент, язык, кэш, цена. Вкладка «Ходы» — раунды Ouroboros,
   вызовы инструментов, узлы графов, вызовы LLM, время и деньги каждого шага; «Мониторинг» — метрики по версиям агента.
4. **Индекс.** Параметры фрагментов и эмбеддингов действуют только после переиндексации `oilo ingest --recreate`:
   разбор PDF берётся из кэша `var/parsed`, заново считаются фрагменты и эмбеддинги (около 50 мин на CPU стенда).
   С нуля база из 6 выпусков строится ~1–1,5 ч.
5. **Шум.** В наборе `evals/datasets/dev.jsonl` 42 кейса: при доле пройденных 80–90% интервал Уилсона 95% — около
   ±9–12 п.п. Разницу меньше этого одним прогоном не доказать: нужны повторы (`--repeats 3`) и сравнение по кейсам.

Меняйте по одному параметру за замер: иначе непонятно, что дало эффект.

## 1. Каталог `config/current/` — поведение инструментов

Строгая схема (`src/oil_ouroboros/catalog.py`): неизвестный ключ, файл без схемы или значение вне диапазона — сервис
инструментов отвечает 503 на `/api/health`, и Ouroboros с ним не поднимется; список проблем — `oilo catalog check`.
Комментарий в строке YAML (разделы llm, retrieval, indexing, web, research, verify, forecast) — это описание параметра
в консоли и в `oilo catalog show`. Слои (поздний переопределяет ранний): слот `CATALOG_SLOT` → `LLM_MODEL_SUBAGENT`
(слой `env`) → `CATALOG_SET` (слой `set`, только разделы llm, retrieval, web, research, forecast, reports). Отпечаток
считается по итоговым значениям и текстам промптов, без комментариев.

### 1.1 Модель субагентов — `llm.yaml`

| Параметр = значение | Что делает · почему так | Больше / вкл. | Меньше / выкл. | Как проверить |
|---|---|---|---|---|
| `subagent.model` = `openai/gpt-6-luna` | Модель узлов `plan` и `select_grade`: план поиска, отбор фрагментов, оценка достаточности. Дешёвая, со стабильным JSON. Действует на профиле openrouter; на gigachat (по умолчанию) модель задаёт `LLM_MODEL_SUBAGENT=GigaChat-3-Ultra` (слой `env`, раздел 2.10) | Сильнее модель — точнее отбор и вердикт достаточности (меньше лишнего веба), но дороже и медленнее | Слабее — ошибки JSON и ремонтные вызовы, хуже отбор | `LLM_MODEL_SUBAGENT=…` + eval: `facts`, `route_web`, цена; «Ходы» → вызовы LLM |
| `subagent.temperature` = 0.0 | Случайность ответов модели; 0 — воспроизводимость | Разнообразнее запросы плана, но прогоны eval хуже повторяются | Меньше 0 не бывает | eval `--repeats 3` |

### 1.2 Поиск по отчётам — `retrieval.yaml`

Цепочка (`rag/retriever.py`): все запросы плана — одной пачкой в Qdrant; в каждом ветки dense и sparse по `prefetch`
кандидатов сливаются RRF, оценки фрагмента по запросам складываются → надбавка последнему выпуску →
`rerank_candidates` кандидатов (при сравнении агентств — с квотой каждому) → порядок по реранкеру, а при
`RERANKER=none` — по RRF → LLM-отбор (узел `select_grade`) видит `research.select_candidates` и оставляет до `top_k`.
Каждое звено не больше предыдущего: поднимать `top_k`, не поднимая звенья выше, бесполезно.

| Параметр = значение | Что делает · почему так | Больше / вкл. | Меньше / выкл. | Как проверить |
|---|---|---|---|---|
| `prefetch` = 40 | Кандидатов из каждой ветки (dense, sparse) до слияния | Полнее на редких терминах, чуть дольше запрос к Qdrant | Быстрее, риск потерять нужный фрагмент | `oilo eval-retrieval`; «Ходы» → `retrieve` |
| `rerank_candidates` = 24 | Сколько кандидатов после RRF и надбавки идёт дальше; при сравнении агентств делится квотой | Больше шансов дожить нужному фрагменту; с cross-encoder на CPU — дольше (время ∝ числу пар) | Дешевле, но теряется полнота — особенно в сравнениях агентств | eval кейсы сравнения (`R09`, `cites_orgs`) |
| `rerank_max_length` = 512 | Длина пары «запрос + фрагмент» для cross-encoder, токенов; только при `RERANKER=bge-reranker-v2-m3` | Точнее для длинных фрагментов, время на CPU ∝ длине | Быстрее, хвост фрагмента обрезается | время `retrieve` с bge-реранкером |
| `top_k` = 6 | Сколько фрагментов отбор оставляет в пакете для ответа | Больше контекста и ссылок, но каждый фрагмент — ~450 токенов в каждом раунде агента и больше шума | Дешевле, риск, что в сравнении не хватит фрагмента второго агентства или выпуска | eval `facts`, `cites_orgs`; цена ответа |
| `latest_edition_bonus` = 0.15 | Надбавка оценке фрагмента последнего выпуска серии (и при отборе кандидатов, и в итоговой оценке), если выпуск не назван в вопросе | Ответ чаще по свежему выпуску, даже если прошлый совпадает чуть лучше | Прошлый выпуск может перебить новый — устаревшие цифры в ответе | eval по последним выпускам; «Ходы» → `bonus` у фрагментов |

### 1.6 Проверка ответа — `verify.yaml`

Проверка — граф `graphs/verify_answer.py`, кодом, а не моделью. Там же финал хода консоли: что увидит пользователь,
решает сервис инструментов (`POST /api/finalize`) — перепроверяет ответ агента по доказательствам этого хода, ставит
метки и список источников; если правка агента проверку не прошла, показывается последний проверенный черновик.

| Параметр = значение | Что делает · почему так | Больше | Меньше | Как проверить |
|---|---|---|---|---|
| `max_issues` = 12 | Сколько замечаний проверка возвращает агенту для правки | Полнее обратная связь, длиннее результат инструмента | Агент исправит часть — лишние повторные проверки | «Ходы» → число `verify_answer` на ход |
| `max_checks` = 2 | Сколько проверок черновика на ход. Счёт ведёт сам `verify_answer` по пакетам хода (пакет диалога не в счёт) и после последней неудачной велит не проверять снова, а завершать: при `render=false` (ход консоли) — черновиком без неподтверждённых цифр, его перепроверит финал хода; при `render=true` (чат владельца, Telegram, расписание) — текстом для показа, где неподтверждённое помечено. Регламент агента числа не содержит — он ссылается на сигнал инструмента. Слоем `CATALOG_SET` не меняется | Больше шансов на чистый ответ, но каждая проверка — раунд агента | Быстрее, но чаще ответ с неподтверждёнными цифрами без правки | «Ходы» → `verify_answer` на ход; журнал MCP → поле `check` |
| `neighbours_hours` = 0.25 | Запасной путь без `pack_ids`: окно «соседей» цитаты, ч. С обязательными `pack_ids` почти не используется | Риск принять доказательство чужого разговора | Меньше «соседей» для перепривязки ссылок | — |

|---|---|---|---|---|

### 2.10 LLM-профили: OpenRouter и GigaChat

Профиль — набор моделей агента и субагентов и путь, которым они идут (`deploy/llm/<профиль>.env`). Переключение:
`python scripts/llm_profile.py openrouter` (или `gigachat`) меняет модели в `.env`, добавляет или убирает профиль
compose и создаёт внутренний токен прокси. Затем `docker compose up -d && docker compose restart ouroboros`; на стенде —
`python scripts/deploy.py up && python scripts/deploy.py restart ouroboros`. Код, регламент, база отчётов и журнал
доказательств от профиля не зависят. Модель входит в версию агента и в отпечаток каталога, поэтому замеры разных
профилей не смешиваются.

| Профиль | `OUROBOROS_MODEL` | `OUROBOROS_MODEL_LIGHT` | `LLM_MODEL_SUBAGENT` |
|---|---|---|---|
| `gigachat` (по умолчанию) | `GigaChat-3-Ultra` | `GigaChat-2` | `GigaChat-3-Ultra` |
| `openrouter` | `anthropic/claude-haiku-5.5` | `deepseek/deepseek-v4.1-flash` | пусто — `openai/gpt-6-luna` из `llm.yaml` |

| Параметр = значение | Что делает · почему так | Если изменить | Как проверить |
|---|---|---|---|
| `LLM_PROFILE` = `gigachat` | Имя текущего профиля; его пишет переключатель | Вручную не меняйте: модели и сервисы переключает скрипт | консоль → «Параметры» |
| `GIGACHAT_CREDENTIALS` | Ключ авторизации GigaChat API из личного кабинета Сбера; его знает только контейнер `gpt2giga` | Пусто — прокси не получит токен, вызовы GigaChat падают | `docker compose logs gpt2giga` |
| `GIGACHAT_SCOPE` = `GIGACHAT_API_PERS` | Доступ: `GIGACHAT_API_PERS` — физлица (Freemium), `GIGACHAT_API_B2B` / `GIGACHAT_API_CORP` — юрлица | Не тот scope — отказ авторизации | то же |
| `GPT2GIGA_API_KEY` | Внутренний токен шлюз ↔ прокси; создают `init_env.py` и `llm_profile.py` | — | `/health` шлюза → `gigachat.key_set` |
| `GIGACHAT_MAX_CONNECTIONS` = 1 | Одновременных запросов прокси к GigaChat: во Freemium — один поток, остальные ждут в очереди прокси | Больше — быстрее eval, но при одном потоке — отказы 429 | время ходов в «Мониторинге» |

Чем профиль gigachat отличается в работе:
- **Деньги и квота.** Freemium бесплатен: шлюз пишет $0, а расход виден в токенах журнала шлюза. Полный eval —
  ~4 млн токенов Ultra (замер на 42 кейсах); кэш промпта квоту не экономит.
- **Инструменты.** Прокси игнорирует `parallel_tool_calls`: агент вызывает по одному инструменту за раунд, ход дольше.
- **Качество.** Полный набор 2026-10-26 (всё на Ultra, версия `aa4564a49bd8`): 35/42 = 83%, цифры показанного ответа
  подтверждены на 100% ([отчёт](../report.md#качество)). Слабые места — лишние отказы «вне компетенции» и сам агент:
  на замечания проверки он присылает почти тот же черновик, а лимит `verify.max_checks` для него совещательный —
  изредка он проверяет сверх лимита. По умолчанию профиль всё же gigachat: Freemium бесплатен и не
  нужен ключ с зарубежной оплатой. Если на вкладке «Качество» этого мало — профиль openrouter; замеры профилей не
  смешиваются (модель входит в версию агента).
- **Рассуждения выключены** (`GPT2GIGA_DISABLE_REASONING=True` у прокси). Ouroboros просит `reasoning_effort`, а
  GigaChat 3 Ultra в этом режиме зацикливался: пересказывал промпт в поле рассуждений, пока не исчерпывал весь
  `max_tokens`, и не давал ответа. Без рассуждений отвечает и зовёт инструменты нормально.
- **Контекст.** У GigaChat 3 Ultra окно около 128 тыс. токенов: ход консоли (40–60 тыс.) помещается, длинные задачи
  владельца — не всегда.
- **TLS.** Серверы Сбера подписаны корнем Минцифры (`deploy/gigachat/russian_trusted_root_ca.pem`, отпечаток — в
  файле); ему доверяет только контейнер `gpt2giga`.

## 5. Что меняется вместе

- **Время.** Вызов субагента — до `timeout_s × (1 + retries)` = 90 с; `research` — план и отбор (два вызова) плюс
  веб до `WEB_TIME_BUDGET_S` = 40 с (при `needs_freshness` веб идёт параллельно с поиском по отчётам). Вызов
  инструмента обрезает `MCP_TOOL_TIMEOUT_SEC` = 180 с, ход — `TURN_TIMEOUT_S` = 480 с. В худшем случае `research`
  длиннее 180 с; `hedge_after_s` делает такой случай редким. Поднимая таймауты, держите
  `субагент < инструмент MCP < ход`.
- **Деньги.** Три потолка, и два из них жёсткие: `GATEWAY_BUDGET_USD` — по журналу шлюза за всё время его тома;
  `OUROBOROS_TOTAL_BUDGET` — по журналу Ouroboros за всё время его тома, на нуле задачи встают на паузу;
  `OUROBOROS_PER_TASK_COST_USD` — пауза одной задачи. Оба жёстких лимита копятся без периода: следите за остатком
  и поднимайте их в `.env`.
- **Поиск.** `prefetch` → `rerank_candidates` → `research.select_candidates` → `top_k`: поднимать звено имеет смысл,
  только если предыдущее не меньше.
- **Индекс.** `EMBEDDER`, `EMBED_MODEL`, `indexing.chunk_tokens` действуют после `oilo ingest --recreate`;
  `DOCLING_TABLE_MODE` — после нового разбора (кэш `var/parsed` удалить).
- **Инструменты MCP.** Изменили описание или аргументы инструмента — перезапустите Ouroboros: его воркер читает список
  инструментов MCP один раз (поэтому `ouroboros` стартует только после здорового `tools`).
