# Архитектура oil_ouroboros

Факты об Ouroboros v7.7.0 сверены с исходным кодом релиза (коммит e41596c, репозиторий razzant/ouroboros).

## 1. Задача

Требования ([requirements.md](../requirements.md)): агент «Старший аналитик нефтегазового рынка».
- Отвечает на отраслевые вопросы.
- Прогнозирует цены нефти расчётным модулем и сам решает, когда его вызывать.
- Ищет гибридно: отчёты (RAG) приоритетны, интернет — дополнение, жёлтая пресса отфильтрована.
- В ответе маркирует источники: `[Отчёт OPEC MOMR, октябрь 2026, с. 23]`, `[Источник: reuters.com, web, …]`.
- Технически: Python ≥3.10, LangChain/LangGraph, простой UI, Docker одной командой, `.env`, README, ≥5 демо-диалогов.

Агент — Ouroboros (официальный образ, без форка). Все его инструменты — графы LangGraph: RAG, веб, прогноз, проверка.
Параметры видны и версионированы, качество измеряется — это основа самоулучшения агента.

## 2. Решение в одном абзаце

Ouroboros в своём контейнере — **мозг**: ведёт диалог, планирует, решает, какие инструменты звать, и пишет ответ.
Роль задаёт его память: `identity.md`, `WORLD.md` и регламент `knowledge/overview.md`. Инструменты живут в сервисе
**tools** и подключены по MCP (streamable HTTP); каждый — граф LangGraph. Приоритет источников, проверка цифр и
финал хода (что увидит пользователь консоли) — **код в инструментах**, а не воля модели. Все вызовы LLM системы идут
через **LLM-шлюз** с жёстким лимитом денег, журналом и кэшем промпта (для моделей `anthropic/*` профиля openrouter).
Входы:
- **консоль** — для пользователей: отдельный разговор у каждого, проверенный ответ с метками источников, ходы,
  мониторинг, eval;
- **канал владельца** (профиль `owner`) — собственный UI Ouroboros и Telegram: Ouroboros как есть, со всеми его
  инструментами ([owner.md](../guide/owner.md)).

## 3. Контейнеры, сети, секреты

![Архитектура](../../ui/architecture.svg)

Что делает каждый сервис и зачем он отдельный — поля `x-role` и `x-why` в [docker-compose.yml](../../docker-compose.yml),
кто к кому обращается — `x-links` там же. Из них вкладка консоли «Архитектура» строит интерактивную карту системы
(режимы «Связи» и «Развёртывание»; эксплуатация — [operations.md](../guide/operations.md)), а
графы инструментов — из кода (`/api/graphs`: узлы, их вид, параметры каталога, ветвления); тесты проверяют, что
описан каждый сервис, сеть и том, а концы связей существуют. Свои образы —
три: `oilo/app` (шлюз, инструменты, консоль, засев, egress, schedules), `oilo/ml` (BGE-M3 и Docling) и `oilo/ouroboros`
(официальный Dockerfile Ouroboros на закреплённом коммите).

- **Ядро и профили.** `docker compose up -d` запускает ядро: `qdrant`, `encoder`, `gateway`, `tools`, `bootstrap`,
  `ouroboros`, `console`. Профиль `owner` добавляет канал владельца (`ouroboros-ui`, `egress`, `schedules`), профиль
  `gigachat` — прокси `gpt2giga` (LLM-профиль по умолчанию); шаблон `.env` включает оба. Хост без прямого выхода в
  интернет подключает `deploy/compose/proxy.yml`.
- **Сети.** `ouroboros` — только во внутренней сети `agent` без выхода наружу. Шлюз, инструменты, консоль,
  `ouroboros-ui` и egress — в `agent` и в `oilo` (сеть с выходом); `encoder`, `qdrant`, `gpt2giga`, `bootstrap` — только
  в `oilo`; `schedules` — только в `agent`. Наружу ходят шлюз (LLM), инструменты (веб, сайты агентств, цены EIA,
  котировки Мосбиржи iss.moex.com), кодировщик (модели HuggingFace) и gpt2giga; агент — только через `egress` к
  хостам `EGRESS_ALLOW`. С `deploy/compose/proxy.yml` все они идут через прокси организации, кроме gpt2giga: серверы
  GigaChat в РФ, и на стенде он ходит к ним напрямую.
- **Секреты.** `.env` общий, поэтому в compose у каждого сервиса на образе `oilo/app` чужие секреты обнулены
  (`x-no-secrets`), а свои перечислены явно; кодировщик, egress и gpt2giga `.env` не получают. `tools` читает
  недоверенный веб-текст, поэтому у него нет ни пароля Ouroboros, ни токена журнала LLM.
- **Готовность.** `ouroboros` здоров по `supervisor_ready`. Он стартует после здорового `tools`: рабочий процесс
  читает список инструментов MCP один раз. `encoder` отвечает 503, если модели не загрузились.

## 4. Агент на Ouroboros

### 4.1 Особенности Ouroboros v7.7.0 и как решение под них устроено

- **Неизменяемое ядро контекста.** В каждый запрос идут `prompts/SYSTEM.md` и `BIBLE.md` (~22 тыс. токенов: «I am not
  a bot… Not an assistant») и карты архитектуры (~7 тыс. в режиме low). Меньше ~29 тыс. токенов без форка не бывает.
- **Память** (`<data>/memory/`): `identity.md`, `WORLD.md`, `knowledge/overview.md` (в каждом контексте как «Shared
  understanding»), `knowledge/patterns.md`. Штатные `update_identity` и `knowledge_write` меняют её с журналами
  `identity_journal.jsonl` и `knowledge_history.jsonl`.
- **Задачи API** — вход для программного клиента: `POST /api/tasks` (`description`, `disabled_tools`, `memory_mode`
  shared | forked | empty, `metadata`, `execution_timeout_sec`), результат — `GET /api/tasks/{id}`. Контекст диалога и
  правила хода консоль кладёт в текст задачи: он под кэшем промпта (поле `context` идёт в Runtime context —
  динамическую часть без кэша).
- **Что ещё в контексте задачи.** В режиме `low` в ядро всегда входят карты книг ARCHITECTURE и DEVELOPMENT
  (~7 тыс. токенов). `memory_mode=forked` и `empty` изолируют запись памяти, но не чтение: контекст собирается из
  общего корня памяти, и задача без проекта видит разговор владельца в комнате Main. Штатного рычага у задачи API для
  этого нет.
- **Завершение.** `finish_task` в одной пачке с другими вызовами Ouroboros не принимает (`unobserved_tool_results`):
  агент завершает отдельным шагом, когда прочитал результат проверки. Если приёмка Ouroboros держит завершение дольше
  30 с, консоль закрывает ход сама (`completed_by_console`) и останавливает задачу; пауза по потолку денег на задачу
  тоже закрывает ход (`agent.py`).
- **Ход и журнал шлюза.** Вызов модели не несёт id задачи: консоль ставит в текст задачи служебную метку
  `oilo-turn <id>`, по ней шлюз относит каждый вызов LLM к ходу; та же строка в тексте пользователя обезвреживается.
- **Чат Ouroboros** (`/ws`) рассылает сообщения всем открытым вкладкам и не умеет отключать инструменты: это канал
  владельца, а не пользователей.
- **Инструменты.** Встроенных 140 (~37–45 тыс. токенов схем), глобального белого списка нет: отключение — только
  `disabled_tools` у задачи. MCP: `MCP_SERVERS` (streamable_http, `auth_token`, `allowed_tools`); сессия на каждый
  вызов, описания режутся до 512 символов.
- **Время хода.** За 2 минуты до `execution_timeout_sec` Ouroboros требует финальный ответ без инструментов. Ход
  консоли получает 480 с, чтобы ответ с отчётами и вебом успевал пройти проверку.
- **Кэш промпта.** Ouroboros ставит маркеры кэша Anthropic (`cache_control`) на стабильные блоки системного промпта,
  сообщение задачи и хвост переписки; на маршруте `openai-compatible::` он их снимает, и шлюз возвращает маркеры на те
  же места — только для моделей `anthropic/*` (профиль openrouter). Раунд — ~60 тыс. входных токенов, из них в кэше
  47–61 тыс. (замер на openrouter). На GigaChat шлюз маркеров не ставит: Freemium бесплатен, расход — в токенах.
- **Наблюдаемость.** Поток событий задачи `GET /api/tasks/{id}/events` (SSE: раунды LLM, вызовы инструментов, итог),
  `/api/tasks/{id}`, `/api/settings`. OpenTelemetry и вебхуков нет.
- **Один владелец.** Память общая для всех комнат. Многопользовательность — забота консоли.
- **Сеть.** Рабочие процессы не ходят через системный прокси: LLM — только через шлюз во внутренней сети. Текст чата,
  начинающийся с «/panic», «/evolve» и т. п., исполняется как команда: консоль экранирует ведущий «/».

### 4.2 Как задаётся роль

1. `identity.md` — самоописание от первого лица: «моя работа — анализ нефтегазового рынка, отвечаю через инструменты
   mcp_oil__*, с источниками».
2. `knowledge/overview.md` — регламент аналитика: экспертиза, приоритет источников, протокол инструментов, формат
   ответа, короткие промежуточные реплики. Всегда в контексте.
3. `WORLD.md` — среда развёртывания: контейнер, пользователи, инструменты, веб только через mcp_oil.
4. Текст задачи от консоли — последние реплики разговора, вопрос, язык ответа и правила хода консоли (`TURN_RULES`):
   только её отличия от регламента — `verify_answer` с `render=false` и проверенный черновик со ссылками в
   `finish_task` (метки и список источников ставит консоль), не писать в память, не запускать фоновых задач, плюс
   напоминание: вопрос вне компетенции — только отказ, без инструментов. Протокол — в регламенте, число проверок — в
   каталоге (`verify.max_checks`): одна точка правды для каждого правила.

Засев делает разовый сервис `bootstrap`. Файл памяти он перезаписывает, только если агент его не менял сам (sha засева
в `state/oilo_seed.json`): улучшенный агентом регламент сохраняется.

### 4.3 Ход консоли

Ход по шагам — [how_it_works.md](../guide/how_it_works.md). Коротко: вне компетенции — отказ без инструментов;
отраслевой вопрос — сначала `research`, чистый расчёт — сразу расчётный модуль, текущая цена — сразу `price_quote`;
черновик со ссылками → `verify_answer` → `finish_task` отдельным шагом. Что увидит пользователь, решает финал хода в
сервисе инструментов (`POST /api/finalize`): показываемый текст перепроверяется по доказательствам этого хода, метки и
строку проверки ставит код; не прошедшая проверку правка агента не показывается. В ходах консоли у агента 9 инструментов MCP и из
встроенных только `finish_task`, `knowledge_read`, `knowledge_list`; память — копия на ход (`memory_mode=forked`).

### 4.4 Канал владельца

UI Ouroboros, Telegram, утренняя сводка, настройки владельца и риски этого канала — [owner.md](../guide/owner.md).
Ответы там — с метками источников и строкой проверки: их ставит сам `verify_answer` (текст для показа), финала хода
консоли в этом пути нет.

## 5. Инструменты (сервис tools, LangGraph)

| MCP-инструмент | Граф LangGraph | LLM | Возвращает |
|---|---|---|---|
| `research(question, focus?)` | plan → retrieve → select_grade → [политика веба, код] → web → pack | 2 дешёвых вызова | пакет P#: R# (отчёты), W# (веб), вердикт достаточности, решение о вебе с причиной |
| `search_reports(queries, orgs?, editions?, question?)` | тот же граф без веба: plan (запросы агента, без LLM) → retrieve → select_grade → pack | 1 | R# |
| `search_web(queries, pack_id, freshness?, reason?)` | check_pack → search (провайдеры, уровни доверия, ранжирование) → pack | 0 | W# (и отсеянные с причиной) |
| `forecast_price(benchmark, horizon_months, method)` | compute (загрузка ряда, бэктест, прогноз, интерпретация) → pack | 0 | F#: медиана, интервалы 50/80/95, скилл против случайного блуждания |
| `supply_shock_scenario(delta_mbd, …)` | compute (базовый прогноз + шок) → pack | 0 | F# |
| `price_history(benchmark, start, freq)` | compute → pack | 0 | F# |
| `price_quote(benchmark)` | compute (котировка ISS Мосбиржи, спот EIA) → pack | 0 | F#: фьючерс сорта (Brent, WTI, газ Henry Hub, TTF) ближайшего месяца с единицей и временем сделки, спот EIA с датой, если он есть |
| `verify_answer(answer, pack_ids, question, render?)` | resolve → check → render | 0 | вердикт, замечания, следующий шаг (проверить снова или завершать — по счёту проверок хода), trace; при `render` — текст для показа с метками |
| `list_reports()` | — (обычная функция) | 0 | что в базе, последняя проверка наблюдателя, ближайшие выпуски, текущее время |

- **Журнал доказательств** (SQLite). Глобальные устойчивые id `R#/W#/F#` (дедупликация по фрагменту, URL+тексту,
  инструменту+аргументам) и пакеты `P#`. `verify_answer` берёт тексты источников из журнала: подменить цифру агент не
  может.
- **Что видит проверка.** MCP-вызов не несёт id хода, поэтому агент перечисляет в `verify_answer` пакеты своего хода
  (`pack_ids`, обязательный аргумент). Доказательства этого хода — содержимое этих пакетов, если им не больше 20 минут;
  ссылка вне них чужая: id из соседней задачи или из памяти. Такая проверка не пройдена, и агент правит черновик до
  завершения. В уточнениях доказательства прошлых реплик консоль кладёт в пакет диалога и называет его в тексте задачи.
  Финальная проверка консоли знает доказательства хода точно: по трейсам его вызовов.
- **Проверка цифр** (`evidence/`): каждое число ответа сверяется с текстом процитированного источника этого хода —
  формат, единица и масштаб, направление, расчёт по подтверждённым цифрам. Правила — в шапке `evidence/numbers.py`,
  алгоритм — в шапке `evidence/verify.py`, по шагам хода — [how_it_works.md](../guide/how_it_works.md).
- **Поиск** — все запросы плана одной пачкой в Qdrant; в каждом запросе dense и sparse сливаются RRF, а оценки
  фрагмента по запросам складываются (RRF по определению — сумма).
- **Фрагменты таблиц** — с подписью первой строкой («Table 3a. … Inventories», в ней и единицы; у EIA подпись — заголовок
  раздела или строка перед таблицей) и без выравнивания markdown: пробелы-заполнители и точки раздували таблицу вдвое.
- **Отбор фрагментов** — LLM listwise одним вызовом вместе с оценкой достаточности (узел `select_grade`). Отбор видит фрагмент
  целиком (до 2000 символов) и раздел или подпись таблицы. Cross-encoder на CPU занимает 24–130 с, с GPU —
  `RERANKER=bge-reranker-v2-m3`. Последний выпуск серии получает надбавку уже при отборе кандидатов.
- **Время `research`** — в основном вызовы LLM субагента и веб: `reasoning_effort=low` для JSON-узлов; дублирующий
  запрос через 15 с (`hedge_after_s`) против всплесков задержки у провайдера; при `needs_freshness` веб-поиск стартует
  сразу после плана, параллельно с поиском по отчётам; два веб-запроса идут параллельно, пустая неделя расширяется до
  месяца.
- Результаты MCP — компактный текст для модели. Структура для UI хранится в трейсе; результат каждого графа несёт
  `trace`, у `research` — ещё отпечаток каталога `catalog.ref`.

## 6. Данные

- **Отчёты.** EIA STEO, OPEC MOMR и IEA OMR (публичная часть) — по 2 выпуска в репозитории (`data/reports`,
  источники — NOTICE.md). Новые выпуски скачивает наблюдатель: при старте и каждые `REPORTS_WATCH_HOURS` ч.
  opec.org закрыт проверкой Cloudflare (страницы и PDF), поэтому новые OPEC MOMR загружаются вручную. Наблюдатель
  проверяет последние два выпуска каждой серии (`lookback`) и по обложке — что скачан нужный месяц; старые выпуски
  остаются в базе, приоритет свежего даёт надбавка последнему выпуску. Кодировщик строит базу
  сам; во время eval индекс не меняется.
- **Цены.** Дневные ряды EIA (Brent, WTI; Urals = Brent − сценарный дисконт; спот газа Henry Hub — только рядом с
  котировкой) обновляются при старте сервиса инструментов и каждые `PRICES_REFRESH_HOURS` ч. EIA выкладывает их раз в
  неделю — последнее наблюдение отстаёт до недели. Текущую цену даёт `price_quote(benchmark)`: фьючерс ближайшего
  месяца на Мосбирже для сортов каталога `forecast.quote.instruments` — Brent, WTI, газ Henry Hub, TTF (ISS, без
  ключа, задержка 15 мин; переход на следующий контракт за `forecast.quote.roll_days` дней до экспирации), кэш
  `forecast.quote.cache_s`, при сбое — сохранённая котировка с пометкой, во время eval — без сети. Котировки Urals
  нет.
- **Веб.** Tavily → Brave → DuckDuckGo; уровни доверия доменов 0–3 (курируемая политика и экспертные рейтинги 11 520
  доменов), жёлтая пресса отсеивается; кэш выдачи на `WEB_CACHE_HOURS`.

## 7. Наблюдаемость и мониторинг

Источники:
1. Журнал шлюза: каждый вызов LLM (кто, модель, токены, кэш, $, мс, тела запроса и ответа).
2. Трейсы инструментов: прогон на MCP-вызов, узлы графа, вызовы LLM субагентов, доказательства, решения.
3. Задачи, их поток событий и настройки Ouroboros (`/api/tasks`, `/api/tasks/{id}/events`, `/api/settings`); том данных — только на чтение.

Консоль склеивает **ход** по `task_id` Ouroboros и `trace` каждого инструмента: вопрос, раунды Ouroboros,
MCP-вызовы → графы → LLM, ответ, проверка, деньги и время по слоям, версия агента.

**Версия агента** — отпечаток: релиз Ouroboros, файлы памяти, настройки из живого Ouroboros, шаблон хода,
MCP-инструменты, каталог параметров, база отчётов. Метрики мониторинга и eval группируются по ней.

Метрики: доля подтверждённых цифр и ответов с пройденной проверкой, «ответ = проверенный текст», начало хода по
регламенту (`research_first`: первым — `research`, `list_reports` или расчёт, в том числе `price_quote`), источники
только этого хода, метки, язык, отказы, ошибки инструментов, деньги, p50/p95, доля кэша промпта.

**Офлайн-демо.** `oilo demo` прогоняет 7 демо-сценариев (Д6) через агента и записывает ходы целиком
(`var/demo_turns.json` и `var/demo_dialogs.md`, без объекта задачи Ouroboros); в репозиторий запись переносится
вручную — `data/demo/turns.json` и `docs/demo_dialogs.md`. Вкладка «Демо» проигрывает их по шагам: раунды Ouroboros,
вызовы инструментов, узлы графов, проверка, ответ и подробный ход. Ни агент, ни LLM, ни ключ провайдера для этого не
нужны: проигрыватель работает на чистом деплое.

## 8. Качество (eval)

dev-набор — 42 кейса, каждый — настоящий ход агента через Ouroboros, отдельной задачей с копией памяти. Проверки
детерминированные: маршрут и аргументы инструментов, факты, типы и агентства ссылок, подтверждённые цифры, уровень
доверия веба, отказ, честное «нет данных», язык. Дисциплина протокола («ответ = проверенный текст») считается, но исход
кейса не решает. Отчёт — pass rate с интервалом Уилсона, деньги, p50/p95; сравнение версий — точный McNemar.

**Eval по слоям** (`oilo eval-retrieval`, `src/oil_ouroboros/evals/retrieval.py`) — без Ouroboros: узлы `research` (план → поиск →
отбор) на кейсах с эталонными фактами. Факт найден, если его число с точностью эталона и ключевое слово рядом
(`Fact.near`) есть во фрагменте ожидаемого агентства. Меряются доля фактов в кандидатах и в отборе, охват агентств,
вердикт достаточности и «лишний веб». Планы запросов можно взять из прошлого прогона — тогда сравнивается только
поиск и отбор. Ни журнал доказательств, ни веб не трогаются, данные на время прогона заморожены (`freeze.py`).

## 9. Параметры и самоулучшение

- **Каталог инструментов** (`config/`): строгая схема, слои (слот → `LLM_MODEL_SUBAGENT` → `CATALOG_SET`),
  отпечаток `ref` в каждом трейсе, `CATALOG_SET` для замеров без правки файлов.
- **Агент**: регламент и память меняются штатными `knowledge_write` и `update_identity` с журналами; режимы, модели и
  эволюция — в UI Ouroboros. Любая правка меняет версию агента.
- **Цикл улучшения**: агент (или владелец) меняет регламент, параметры или код, eval через того же агента сравнивает
  версии, решение принимает человек. Эталоны eval и проверка цифр агенту недоступны.

## 10. Риски

| Риск | Мера |
|---|---|
| Личность Ouroboros («not an assistant») спорит с ролью | identity, WORLD и регламент в памяти; метрика persona_clean; замер на eval |
| Цена хода (большой системный контекст) | отключение лишних инструментов в ходах консоли, режим контекста low, кэш промпта через шлюз (модели `anthropic/*` профиля openrouter); на GigaChat Freemium — $0, расход квоты в токенах |
| Деньги | жёсткий лимит шлюза и по вызывающим; GigaChat Freemium бесплатен (квота токенов), для OpenRouter — отдельный ключ с лимитом на проект |
| Лимит веб-провайдера | цепочка Tavily → Brave → DuckDuckGo, пометка в трейсе |
| CPU-кодировщик и разбор PDF | разовая сборка базы, кэш разбора, докачка только недостающих выпусков |
| Ouroboros — агент одного владельца | диалоги пользователей хранит консоль; ход — отдельная задача API с копией памяти |
| Владелец меняет агента в UI или Telegram | так и задумано: версия агента берёт настройки из живого Ouroboros, мониторинг и eval показывают эффект; интеграцию засев восстанавливает |
| Команды «/panic» в тексте чата консоли | консоль экранирует ведущий «/» |
| Канал владельца без ограничений консоли (shell, веб в общей памяти) | вне ядра — профиль `owner`; egress только к разрешённым хостам; меры для продуктива — [owner.md](../guide/owner.md#риски-канала-владельца) |
